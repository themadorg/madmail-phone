# Server invitations

Invite belongs to the selected immutable server ID. Local requests use the owned engine's loopback listener; remote requests use the pinned, authenticated SSH tunnel. The guest-facing HTTPS origin is a separate, editable per-server preference. Credentials are never sent to that origin by the management app.

## Supported flows

- **Invite link:** POST `/admin/registration-token` with use limit, label and optional lifetime. QR and copy/share contain the guest-facing `/inv/<encoded-token>` URL. Guests open Madmail's web flow and create separate accounts. List, refresh, usage, pending reservations, expiry and revocation use the real admin API.
- **Personal account QR:** create a one-use token, then POST `/new` through loopback/SSH. Use the returned `dclogin_url`, preserve credentials, TLS modes and actual ports, and substitute the explicitly selected guest-facing host. Set SMTP certificate policy to match IMAP, as Delta Chat requires. A QR belongs to one person; it is not a second-device transfer or group invitation.
- **Local account readiness:** before displaying a phone-hosted account QR, authenticate IMAP once and then SMTP over loopback TLS pinned to the owned engine certificate. This settles the one-use token before Delta Chat connects both protocols concurrently. The token is consumed at QR creation; its expiry is not an account expiration or a way to revoke that account. A failed readiness check withholds the QR and preserves the existing ambiguous-result recovery flow. Remote provisioning still needs an upstream atomic first-login fix.
- **Presentation:** white QR quiet zone in both themes; enlarged view keeps the screen awake; sensitive clipboard; text and PNG Android share chooser; open personal setup in a compatible Delta Chat handler. No message is sent automatically.
- **Lifecycle:** unknown/unloaded/revoked/exhausted/expired invite links are not presented as active. Server mutations are never automatically retried. Failed mutations tell the host to refresh before creating another invitation. Revoking a token does not delete existing accounts.

The bundled managed server uses self-signed TLS. The create sheet explains that account QR certificate settings accept it; browser invitations may show a certificate warning. This is not a claim of public CA validation. LAN hosts must keep guests on the same reachable network and update the origin when their address changes. CGNAT Wi-Fi addresses are valid LAN candidates too.

Account QR payloads and selected invitations stay in memory, scoped to the server. Explicit PNG sharing creates a private cache file exposed by a narrow FileProvider URI grant; older share files are removed on subsequent sharing. Do not claim these intentionally shared images are memory-only. Account credentials cannot be recovered after the app process ends; hiding a QR does not revoke an account.

## Protocol evidence

- Madmail source `22db4602768364955670b0f08dd97f03db6e22cc`: `chatmail-www` exposes POST `/new`, not the GET endpoint expected by URL-form DCACCOUNT. Therefore `/new` is not blindly wrapped in DCACCOUNT.
- Admin web `1cc77414e30a38d573bf40b137135a658e866f6d`: `/admin/registration-token`, `max_uses`, `expires_in`, `comment`, pending reservations, status, and `/inv/<token>`.
- Delta Chat URI specification: https://github.com/deltachat/interface/blob/main/uri-schemes.md — DCLOGIN custom hosts/ports/TLS and matching `ic`/`sc`. Contact/group SecureJoin and device-transfer codes belong to the Delta Chat client's encryption identity and are not generated by this server manager.

## Verification and limits

Unit tests cover endpoint validation, encoding, IPv6, certificate policy, custom ports and QR encode/decode round trips. `InvitationDeviceTest` creates temporary real accounts on the phone, validates returned ports, authenticates with the engine's pinned certificate, checks token use, and deletes test accounts and invitations. Its concurrent-login test verifies that four fresh accounts survive repeated parallel authentication after provisioning. `LocalDeliveryDeviceTest` submits a protocol fixture to two recipients and retrieves both through IMAP, exercising Android's copy fallback for CAS storage and fan-out. The SSH fixture also creates an account through the real remote engine, checks returned QR host/ports and token use, then removes its test records. A separate controller test verifies Wi-Fi discovery, TCP listener access and duplicate-submission suppression. The SSH fixture uses a service shim; it does not prove production VPS firewall access or a live Tailscale connection.

### Delta Chat 2.64 on Pixel 6a

To create a separate profile, copy the account QR in Madmail, then choose Delta Chat's profile switcher → Add Profile → Create New Profile → Use Other Server → Scan Invitation Code → Paste from Clipboard. Give the profile a name and create it. Opening a `dclogin:` link directly while an existing profile is active opens **Add Relay** instead; do not use that route when the guest wants an independent profile.

The first real device attempt exposed an upstream 2.30.5 race: simultaneous IMAP/SMTP first logins can consume a one-use token twice and remove the account. A diagnostic reproduced SMTP authentication failure in two of four fresh accounts. Local provisioning now settles that reservation before publishing credentials. This is a client-side mitigation, not a claim that upstream or remote registration is fixed.

The same device also rejected mail delivery with SMTP 451 because Android denies hard links in app-private storage. The bundled source patch adds copy fallback for denied/unsupported hard links in CAS, local fan-out and the remote queue. It leaves encryption policy and TLS validation unchanged.

Verified 2026-11-01 with the installed patched APK: separate **Madmail Local Test** and **Madmail Local Peer** profiles in Delta Chat 2.64.0, both using `100.64.90.15` and the phone's TLS mail ports. A fresh account from the updated provisioning flow signed in on its first attempt. SecureJoin completed; a text message and reply were received in the opposite profiles, with delivered/read receipts and Delta Chat's end-to-end encryption indicator. The original profile was not given another relay or otherwise changed. Hosting and both test profiles were left available for inspection. This verifies two independent client identities on one physical phone, not another LAN device, an Internet-disconnected network, a live Tailscale route, calls or attachments.

Build, lint and all 20 JVM tests passed. Four local instrumentation tests passed; the opt-in remote fixture was skipped. The new fan-out test failed on the original engine and passed with the patch. Temporary diagnostic accounts and tokens were removed, and USB TCP forwards were closed.

## Guest networks and creation recovery

The address sheet lists actual Wi-Fi, hotspot and VPN interfaces separately, including underlying Wi-Fi while a VPN is the default network. It never infers Tailscale from a `100.64.0.0/10` address: this phone's Wi-Fi itself uses that range. Cellular interfaces are not automatically offered as inbound addresses. Detection currently offers IPv4, matching the managed listeners; IPv6-only access requires a separately configured frontend.

Remote interface discovery runs `ip -o -4 addr show scope global` over the pinned SSH session. A missing `ip` command or disconnected session falls back to manual entry, without replacing the saved address. Public DNS names and Tailscale MagicDNS names can be entered manually. The SSH host is a candidate, not proof of public reachability. Addresses are stored per server; changing one regenerates the displayed link or personal QR host and leaves the server's account identity intact.

The explicit check opens TCP connections from the phone to the selected HTTPS port and managed IMAP/SMTP ports (11993/11465), without tokens or account credentials. It does not verify TLS, proxy port mappings, firewall policy for another guest, or public Internet reachability. VPN guests need a permitted route to the host; exit-node users may need LAN access enabled for Wi-Fi sharing. No firewall, VPN or router configuration is changed automatically.

Creation now belongs to a per-server coroutine owner rather than a composable screen. It survives tab/server navigation, rejects duplicate in-flight submissions, and retains the result in memory until the UI consumes it. An app-process death still loses secret results; inspect server invitations/accounts rather than retrying blindly. Explicit HTTP rejection, an invitation created before account failure, and an uncertain mutation are presented differently. Uncertain creation requires reviewing invitations/accounts before another attempt.

### Managed browser invitation limitation

A real GET of the bundled 2.30.5 `/inv/...` page through the phone's Wi-Fi address rendered `const host = "madmail.local"`. Upstream `client_connect_host` prioritizes `primary_domain`, which this manager sets to preserve the server's account domain. Merely changing the link's HTTPS origin does not change that page's mail host. Removing the primary domain would also change account registration identity, so the app does not silently rewrite it.

Account QR is now the default and supplies the selected guest host explicitly. Before creating a browser-link token, the controller reads the managed web template through loopback/SSH and refuses placeholder or unrecognized mail-host output, with guidance to choose Account QR. No token is created by that failed preflight. A server with a configured real mail hostname can still create browser links. Making the browser route adapt reliably to several guest networks while retaining a stable account domain requires an upstream advertised-client-host change; it is not claimed fixed by the Android address picker.
